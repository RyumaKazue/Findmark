# Codebase Mental Model

## このスキルの目的

AI がコードを書き、人間がレビューする。この分業が成立する条件はただ一つ、**レビューする人間の頭の中に、そのプロダクトの動くモデルがあること**だ。モデルがなければ、レビューは「差分がそれ単体で綺麗か」の判定に堕ちる。それは通る。そして壊れる。

人間の頭にモデルを載せる最短経路は**図**だ。文章は線形で、読んでいる途中の部分しか意識に載らない。図は空間なので、全体と部分を同時に保持できる。だからこのスキルの成果物は「図が主役で、文章はその注釈」という構成を取る。文章が長くなり始めたら、それは図に落とせていないというサインだ。

そして図の軸は**処理**に置く。構造（ディレクトリ、クラス階層）の図は覚えられない。人間が覚えられるのは「何かが起きて、こう流れて、こうなる」という因果の連なりだからだ。

## 作るもの

**全体図1枚 ＋ 主要な処理ごとに必ず2枚。** 図種は固定で、フローごとに選び直さない。

| | 図種 | 何を描くか | この図が答える問い |
|---|---|---|---|
| **全体図** 1枚 | `flowchart` | 処理フローの一覧と、それらが共有するモジュール・データ | このプロダクトはどんな仕事をする機械か |
| **A. 処理の流れ** 各1枚 | `sequenceDiagram` | 起動から完了までの時系列・分岐・失敗経路 | 誰が誰を呼び、何が返り、どこで失敗するか |
| **B. 依存グラフ** 各1枚 | `flowchart` | そのフローが触るモジュールと依存の向き・共有点 | 何に依存していて、変えると何に波及するか |

**なぜ2枚必要か。** 処理は時間軸と空間軸の2つの側面を持つ。sequenceDiagram は「いつ何が起きるか」を見せるが、モジュール同士の依存の形は見えない。依存グラフは「何に支えられているか」を見せるが、順序と失敗経路が消える。人間が処理を頭の中で再生するにはこの両方が要る。片方だけだと、予測はできても影響範囲が読めない（あるいはその逆）になる。

**図種を固定する理由。** フローごとに図の種類が変わると、読み手は図を読むたびに「これはどういう読み方をする図か」を判断し直すことになり、その分だけ内容の理解に使える容量が減る。同じ形式が並んでいれば、2枚目以降は読み方を考えずに中身だけを見られる。**一貫性は理解速度そのものであり、図種の最適化より優先する。**

全体図だけだと抽象的すぎて予測に使えない。個別の図だけだと、読み手はそれらの関係を自力で組み立てる羽目になり、たいてい失敗する。

## 手順

### 1. 処理フローを洗い出す

これが成果物の質をほぼ決める工程なので、丁寧にやる。

まず**外から起動される点**を全部列挙する。ここに漏れがあると、そのフローは読み手のモデルから丸ごと欠落する。

- UI のイベントハンドラ（クリック、入力、キーボードショートカット）
- ルート定義 / API エンドポイント
- CLI コマンド、サブコマンド
- イベント購読、メッセージハンドラ、Webhook
- 起動時処理、定期実行、ライフサイクルフック
- 外部からのコールバック（OS、ブラウザ、SDK）

`package.json` の scripts、manifest、ルーティングファイル、`addEventListener`/`on(`/`@app.route` などの登録箇所を grep すると機械的に集まる。

次に、これらを**「ユーザーから見て一つの仕事」の単位**にまとめ直す。「クリックハンドラが呼ばれる」は処理フローではない。「ブックマークを検索して結果を表示する」が処理フローだ。粒度の基準は、**そのフローの名前を言ったときに、関係者の間で同じものが思い浮かぶか**。

最後に重要度で並べ、**主要な4〜7本に絞る**。1本につき2枚描くので、7本で全体図と合わせて15枚になる。これが1度に頭へ載る上限だと考えていい。全部描くと1つも覚えられない。落としたものは一覧に名前だけ残し、「必要なら追加で描ける」と伝える。

### 2. 各フローを実際に追う

フローごとに、**具体的な値**を1つ決めて追いかける。「検索クエリが来たら」ではなく「`foo` と入力されたら」。抽象的なまま図を描くと、必ずどこかで嘘が混ざる。

各ステップで押さえること:

- どの関数が呼ばれるか（ファイルと行番号）
- 何が渡され、何が返るか（実際の型名・変数名）
- どこで分岐するか、**失敗したらどうなるか**
- 状態が変わるなら、何がどう変わるか

**正常系だけの図は嘘をつく。** 読み手は「この処理は必ず成功する」というモデルを作ってしまい、エラーハンドリングの抜けた差分を通してしまう。分岐と失敗経路は、正常系と同じ重みで描く。

主張する前に必ず grep で確認する。1箇所の嘘が図全体の信用を壊す。確認できなかったところは図の中に「?」として残し、未解明として書く。

### 3. 図を描く（1フローにつき A・B の2枚）

**図種は選ばない。全フローで A = `sequenceDiagram`、B = `flowchart`（依存グラフ）に固定する。** 「このフローは状態遷移が主だから stateDiagram にしよう」といった最適化をしてはいけない。読み手が得る一貫性のほうが、個別の図の表現力より価値が大きい。

- **A（処理の流れ）** — 時間軸。参加者を実際のモジュール名にし、`alt`/`opt` で分岐と失敗経路を必ず描く
- **B（依存グラフ）** — 空間軸。A に登場したモジュールが**何に支えられているか**を描く。純粋モジュール／副作用を持つモジュール／外部 API を形で描き分け、**他のフローと共有しているノードを強調する**（そこが変更の波及点になる）

A と B は同じフローの表と裏なので、**登場するモジュール名は必ず一致させる**。A に出てくるのに B にいない、あるいはその逆があったら、どちらかの調査が足りていない。

描き方・良い図と悪い図の具体例は同ディレクトリの `diagram-patterns.md` にまとめてある。**図を書き始める前に必ず読むこと。** 図の質がこのスキルの成果物の質そのものなので、パターンを頭に入れてから描く価値がある。

書いたら Mermaid の構文が通るか確認する。壊れた図は 0 点なので、ここは横着しない。

### 4. すべての図に「何の処理か」を明示する

**これは例外なく守る。** 図が複数ある文書で読み手が最も高い頻度で迷子になるのは、「今見ているこの図は、結局どの処理の話なのか」が分からなくなる瞬間だ。そうなると図は理解を助けるどころか、混乱の発生源になる。図は本文と違って前後の文脈を持ち込みにくいので、**1枚1枚が自己完結していなければならない**。

すべての図に、直前にこの4行を置く。

```markdown
**処理**: [動詞で書いた処理名。「〜する」の形]
**起動**: [何が起きるとこの処理が始まるか]
**範囲**: [どこから始まり、どこで終わるか]
**含まない**: [混同されやすいが、この図の外にあるもの]
```

例:

```markdown
**処理**: ブックマークを検索して結果を表示する
**起動**: 検索ボックスへの入力、またはショートカット `Cmd+Shift+F` での起動
**範囲**: `onChange` の発火から、結果リストの描画完了まで
**含まない**: 検索インデックスの構築（→ フロー6「起動時にインデックスを構築する」）
```

「含まない」の欄が特に効く。隣接する処理との境界が引かれて初めて、読み手はその図の輪郭を正しく掴める。境界が曖昧だと、読み手は無意識にスコープを広げて解釈し、間違ったモデルを作る。

さらに、**Mermaid のコード内にもタイトルを埋め込む**（`diagram-patterns.md` の書き方に従う）。図は切り出して Slack に貼られたり、スクショで共有されたりする。その瞬間に何の図か分からなくなるのを防ぐ。

**A・B の2枚は同じ処理の表と裏なので、4行ヘッダはフローの冒頭に1回だけ置く。** 2枚それぞれには、代わりに「この図が答える問い」を1行添える。同じ4行を2回繰り返すと、読み手は差分を探して無駄に時間を使う。

```markdown
### 1-A 処理の流れ
> 答える問い: 誰が誰を呼び、何が返り、どこで失敗するか

### 1-B 依存グラフ
> 答える問い: このフローは何に依存し、変更すると何に波及するか
```

Mermaid 内のタイトルには `A` / `B` の別まで入れる（`"フロー1-A: 索引を構築する — 処理の流れ"`）。切り出された1枚が、どの処理のどちら側の図かまで分かるようにする。全体図も例外ではなく、「このプロダクトの処理フロー全体の配置」であることを明示する。

### 5. 注釈を書く

図に載らない情報だけを文章にする。図を見れば分かることを文章で繰り返さない。

## 出力の構造

Markdown ファイルを1つ作る。この順序で書く。

```markdown
# [プロダクト名] メンタルモデル

## 一行で言うと
[このシステムが何をするものか。技術ではなく目的で。1文]

## 処理フロー一覧
[表。フロー名 / 起動される条件 / 一言で何をするか / 起点のファイル]

## 全体図

**処理**: このプロダクトが持つ処理フロー全体の配置
**起動**: —（個別の処理ではなく、全体の見取り図）
**範囲**: 起点となる入口、主要な処理フロー、それらが共有する中核と外部境界
**含まない**: 各フローの内部（→ 以下の個別の図）

[Mermaid]

### 中核概念
[5〜7個。図に出てくる名前のうち、そのプロダクト固有のものの意味]
- **[コードで使われている実際の名前]** — 何を表すか `path/to/file.ts:42`

---

## フロー1: [動詞で書いた処理名]

**処理**: [この処理は何をするか]
**起動**: [何が起きると始まるか]
**範囲**: [どこから、どこまで]
**含まない**: [混同されやすい隣接処理と、その参照先]

### 1-A 処理の流れ
> 答える問い: 誰が誰を呼び、何が返り、どこで失敗するか

[Mermaid sequenceDiagram]

### 1-B 依存グラフ
> 答える問い: このフローは何に依存し、変更すると何に波及するか

[Mermaid flowchart]

**要点** — [2枚から読み取れない3〜5個の箇条書き。不変条件、罠、意外な点]

## フロー2: [動詞で書いた処理名]
...（全フロー同じ形。図種は変えない）

---

## 全体にかかる不変条件
[個別フローに属さない、システム全体の約束事]

## 意外な点
[経験者の直感が外れる箇所]

## 未解明
[確認できなかったこと]

## 理解できたか確認する
[予測を問う質問3〜5個]
```

### 各セクションの要点

**処理フロー一覧** — 読み手が最初に見る目次であり、「このプロダクトは結局これらの仕事をする機械だ」という要約でもある。ここを読んだだけで輪郭が掴めるように書く。

**全体図** — 個々のフローの中身は描かない。フローと、それらが共有するもの（ストア、状態、外部サービス）の関係を描く。ここで「複数のフローが同じものを触っている」ことが見えるのが重要で、それが後で「ここを変えると何が壊れるか」の判断材料になる。

**中核概念** — そのコードベースが**実際に使っている名前**で書く。コードが `Entry` と呼ぶものを「レコード」と言い換えてはいけない。読み手は最終的にコードを読むのだから、語彙が一致していないと翻訳のコストが永続的にかかる。定義箇所へのポインタをつけ、5秒で裏が取れるようにする。

**フローごとの「要点」** — A・B の2枚の直後に置く。図で分かることを書かない。書くのは:
- **不変条件** — 破られるとバグになる約束。反証可能な形で。「適切に検証される」は無意味。「`url` は `normalizeUrl()` を通ってからでないと Store に入らない (`store.ts:88` で強制)」なら差分を見て判定できる。コードで強制されているのか、単なる規約なのかを区別して書く。規約でしかない箇所は AI が最も破りやすい
- **依存グラフに線としては描けない波及** — B は「誰が誰に依存しているか」までしか描けない。「この定数を変えると別フローの表示が崩れる」「この順序を入れ替えると失敗時に不整合が残る」といった、線では表せない結合をここに書く。呼び出し元は実際に grep して確認する
- **罠** — 2枚を見ただけでは踏みそうな落とし穴

**意外な点** — 高い価値がある。経験のある開発者のデフォルトの期待が外れる場所を書く。名前と実体のずれ（`Cache` と名乗って実は永続化している）、同じことをする方法が2つあり片方が非推奨、意図的に残された歪み、見た目より強い結合。

なぜ重要か: AI が生成するコードは「一般的な常識」に沿って書かれるので、プロダクト固有の逸脱を最も踏み抜きやすい。しかも常識に沿った差分はレビュアーの目にも自然に見える。ここを事前に頭に入れておくことが、レビュー精度を一番大きく変える。

**未解明** — 確認できなかったこと、根拠が弱い推測を正直に書く。読み手がそこを重点的に見る指示になる。省くと、モデルが実際より完全であるかのような誤った自信を与える。

**理解できたか確認する** — 予測を問う質問で締める。「〜とは何ですか」という暗記の確認ではなく、モデルが動いていないと答えられないもの。「新しい検索フィルタを足すならどのファイルを触る?」「Store を経由せず直接 API を呼ぶコードが差分にあったら何が問題?」「この機能を消したら他のどこが動かなくなる?」。答えは書かない。詰まったところが自分のモデルの穴だと分かればいい。

## 範囲の調整

ユーザーが範囲を明示していなければ聞く。デフォルトは全体（プロダクト全部の処理フロー）。

- **特定の機能・サブシステムだけ** — その領域の処理フローだけを描く。全体図はその領域と外の境界を示すものに差し替え、「この機能がやらないこと」と誰がやるかを明記する
- **レビュー直前・特定の差分** — 差分が触っているフローだけを描く。関係する不変条件を抜き出し、**確認すべきことのチェックリスト**にする。差分が暗黙に前提としていることを言語化する（そこが一番危ない）。ただし**差分の良し悪しは判定しない** — レビューするのは人間で、こちらの仕事は判断を奪うことではなく材料を渡すこと

## やってはいけないこと

- **フローごとに図種を変える** — 「これは状態遷移だから stateDiagram」「これは分岐が多いから flowchart」という最適化をしない。読み手は図を読むたびに読み方を切り替えることになり、その負荷が理解の容量を食う。**A = sequenceDiagram / B = 依存グラフ を全フローで貫く**
- **A か B のどちらかを省く** — 「このフローは単純だから1枚で足りる」と判断しない。単純に見えるフローほど、依存グラフを描いて初めて共有ノードの多さに気づく
- **A と B で登場するモジュールが食い違う** — 同じ処理の表と裏なので名前は一致する。ずれていたら調査不足のサイン
- **何の処理か書かれていない図** — 単体で見て何の話か判断できない図は、読み手を助けるどころか迷わせる。フロー冒頭の4行ヘッダ、各図の「答える問い」1行、図中タイトルは例外なく付ける
- **構造の図** — ディレクトリツリー、クラス継承図、層の名前だけの図（UI → Service → Repository）。どのプロダクトにも描けるということは、何も言っていないということ。そのプロダクト固有のものが図に現れていなければ捨てる
- **正常系だけの図** — 分岐と失敗が抜けた図は、読み手に間違ったモデルを植え付ける
- **ファイルごとの目録** — 「`utils.ts`: ユーティリティ関数群」は情報量ゼロ。読み手は `ls` できる
- **コードを読めば分かることの再説明** — 関数の逐条解説は読み手の時間を溶かす
- **裏取りしていない断定** — 1つの嘘が全体の信用を壊す
- **網羅** — 全部描くのは、何が重要か判断する仕事を放棄して読み手に押し付けること。それがこのスキルの仕事の中身だ

## 出力後

ファイルを提示したあと一言だけ添える。「引っかかったところや、もっと細かく見たいフローがあれば言ってください」。メンタルモデルの構築は本質的に対話的で、1回の出力で完成しない。ただし長い後書きは書かない — 読み手はドキュメントを読みに行くのだから。
