# MVP作業単位の実装 (完全自動実行モード)

**重要:** このワークフローは、**2つの承認ゲートの取得を唯一の例外**として、開始から完了まで自動で実行されるように設計されています。各ステップは完了後、ただちに次のステップへ移行してください。承認ゲート以外では、思考の途中でユーザーに確認を求めたり、作業を中断したりしないでください。

**このコマンドの位置づけ（`add-feature` との違い）:**
- `add-feature` は「任意の新機能」を、ユーザーが指定した機能名に基づいて実装するコマンドです。
- 本コマンドは **MVP完成のためのロードマップである `docs/mvp-development-flow.md` を唯一の指示元** とし、その「作業単位一覧」「進捗」表に基づいて **次に実施すべき作業単位を自動特定** し、実装します。
- したがって **このコマンド自身が「何を実装するか」を指示・定義する必要はありません**。実装対象・受け入れ基準・対象領域・依存関係は、すべて `docs/mvp-development-flow.md`（および同書が引用する永続ドキュメント）から取得します。

**2つの停止ポイント（これ以外では停止しない）:**
1. **ステップ4.5（計画承認ゲート）:** ステップ4でステアリングファイル（`requirements.md` / `design.md` / `tasklist.md`）を生成した後、ステップ5(実装)に進む前に、**必ずユーザーの承認を得なければなりません**。承認を得るまで、いかなる実装作業も開始してはいけません。
2. **ステップ7.5（受け入れ承認ゲート）:** ステップ7で自動テストがパスした後、ステップ8(振り返り)・ステップ9(コミット & `dev` マージ)に進む前に、**実装が想定通りであることについてユーザーの受け入れ承認を得なければなりません**。これは `steering` スキルの「ゲート2（受け入れ承認）」に対応します。承認を得るまで、振り返り・コミット・マージ等の後続作業を開始してはいけません。

**モデル運用方針（推奨: 計画=Opus / 実装=Sonnet）:**

本ワークフローは、**フェーズごとに担当モデルを変える**ことを想定している。モデルはコマンド側では自動切り替えできない（frontmatter の `model:` は意図的に設定しない）ため、**制御がユーザーに戻る2つの承認ゲートを切り替え境界**とし、ユーザーが手動で `/model` を実行して切り替える。

| フェーズ | 対象ステップ | 推奨モデル |
|---------|-------------|-----------|
| 計画（要件・設計・タスク分解） | ステップ1〜4.5 | **Opus** |
| 実装（コーディング・検証・テスト） | ステップ4.6〜7 | **Sonnet** |
| 受け入れ・振り返り・コミット | ステップ7.5〜9 | **Opus**（判断・ドキュメント更新のため計画側に戻す） |

このため、**各承認ゲートの提示メッセージには、次フェーズの推奨モデルと `/model` 切り替えの案内を必ず含める**こと（ステップ4.5・7.5に明記）。切り替えはユーザーの操作であり、コマンドが強制するものではない。ユーザーが切り替えない場合はそのまま続行してよい。

**引数:** 省略可。
- **省略時（推奨）:** `docs/mvp-development-flow.md` の「進捗」表から、依存が解決済みで未着手の**次の作業単位を自動特定**する。
- **指定時:** 特定の作業単位ID/名（例: `/implement-unit U5` または `/implement-unit alias-store`）を渡すと、その作業単位を対象にする。指定単位の依存が未完了の場合はステップ1で警告する。

## ステップ1: MVP開発フローの参照と対象作業単位の特定

**このコマンドの起点。`docs/mvp-development-flow.md` を唯一の指示元として、今回実装する作業単位を確定する。**

> **モデル確認（推奨）:** ここからステップ4.5までは計画フェーズのため **Opus** での実行を推奨する。現在のセッションが Opus でない場合は、作業開始前に `/model opus` への切り替えをユーザーに促す（切り替えなくても続行は可能）。

1. `docs/mvp-development-flow.md` を読み込み、以下を把握する:
  - 「作業単位一覧」表（各単位の概要・対応MVP機能・依存・受け入れ基準・主な対象領域）
  - 「開発フロー（順序と依存）」の依存グラフと推奨実装順
  - 「進捗」表（各単位の状態と steering ディレクトリ）

2. 今回の対象作業単位を確定する:
  - **引数が指定されている場合:** その作業単位を対象とする。
  - **引数が省略されている場合:** 「進捗」表で**状態が「未着手」**かつ、依存グラフ上の**依存単位がすべて「✅ 完了」**である作業単位のうち、**推奨実装順で最も先頭のもの**を1つ選ぶ。

3. 依存の充足を検証する:
  - 対象作業単位の「依存」列に挙がる全単位が「進捗」表で「✅ 完了」であることを確認する。
  - **依存が未充足の場合:** その旨（どの依存が未完了か）をユーザーに提示し、先に解決すべき単位を案内したうえで処理を停止する。自己判断で依存を飛ばして実装を進めてはならない。

4. タスクコンテキストを確立する（以降のステップで一貫して使用する）:
  - 作業単位ID / 作業単位名: 例 `U5` / `alias-store`（`docs/mvp-development-flow.md` の記載どおり）
  - 日付: `[現在の日付をYYYYMMDD形式で取得]`
  - ステアリングディレクトリパス: `.steering/[日付]-[作業単位名]/`
5. 上記ステアリングディレクトリを作成する。
6. 以下の3つの空ファイルを作成する:
  - `[ステアリングディレクトリパス]/requirements.md`
  - `[ステアリングディレクトリパス]/design.md`
  - `[ステアリングディレクトリパス]/tasklist.md`

## ステップ2: プロジェクトと引用元ドキュメントの理解

1. `CLAUDE.md`を読み、プロジェクトの全体像を把握する。
2. `docs/`ディレクトリ内の永続ドキュメントを確認し、関連する設計思想やアーキテクチャを理解する。
3. **対象作業単位が引用する箇所を重点的に読む。** `docs/mvp-development-flow.md` の当該単位行が参照する PRD の該当機能・`functional-design.md` のコンポーネント設計・`architecture.md` のレイヤー方針・`repository-structure.md` の配置先を特定し、実装の前提を固める。

## ステップ3: 既存パターンの調査

1. `docs/mvp-development-flow.md` の当該単位「主な対象領域」列に挙がるパス、および関連キーワードでソースコードを検索する。
  ```bash
  Grep('[作業単位に関連するキーワード]', 'src/')
  ```
2. 検索結果を分析し、既存の実装パターン、命名規則、コンポーネントの利用方法、既に完了した依存単位（例: 上流の Store / Service）との接続点を特定する。

## ステップ4: 計画フェーズ (ステアリングファイルの自動生成)

1. `Skill('steering')`を**計画モード**で実行し、ステップ1で作成した3つのファイル (`requirements.md`, `design.md`, `tasklist.md`) の内容を生成する。
  - **受け入れ基準は `docs/mvp-development-flow.md` の当該単位「受け入れ基準」列を `requirements.md` に写し取り**、引用元（PRDの該当機能・`functional-design.md` のコンポーネント設計）へのリンクを併記する。
  - `design.md` は当該単位の「主な対象領域」と依存単位のインターフェースに整合させる。
  - `tasklist.md` は当該単位のスコープに閉じ、他単位の作業を取り込まない。
2. **生成が完了したら、決して自動でステップ5に進んではならない。ただちにステップ4.5に進み、ユーザーの承認を求めること。**

## ステップ4.5: 承認ゲート (実装前の必須確認)

**このステップは、このワークフローにおける唯一の停止ポイントです。ユーザーの明示的な承認を得るまで、実装（ステップ5以降）を絶対に開始してはいけません。**

1. 生成した3つのステアリングファイルの要点をユーザーに提示する:
  - 対象作業単位（ID / 名 / 対応MVP機能）
  - `requirements.md`: 受け入れ基準（mvp-development-flow から写した内容）の概要
  - `design.md`: 設計方針の概要
  - `tasklist.md`: これから実行するタスク一覧
2. ユーザーに対し、これらの内容で実装を進めてよいか、明示的に承認を求める。**あわせて、次フェーズ（実装）の推奨モデルと切り替え方法を案内する。**
  - 例: 「作業単位 `[ID 作業単位名]` のステアリングファイルを作成しました。この内容で実装を進めてよろしいですか？ 修正が必要な場合はご指示ください。\n承認後は実装フェーズに入ります。実装は **Sonnet** を推奨するため、承認前に `/model sonnet` への切り替えをおすすめします（切り替えなくても続行可能です）。」
3. **ユーザーの応答を待つ。ここで必ず処理を停止すること。**
  - **承認された場合** (例: 「OK」「承認」「進めて」など肯定的な応答): ステップ4.6(ブランチ作成)に進む。ユーザーがこの停止中に `/model sonnet` へ切り替えていれば、以降は Sonnet で実行される。
  - **修正を求められた場合:** 指示に従ってステアリングファイル（`requirements.md` / `design.md` / `tasklist.md`）を修正し、再度このステップ4.5で承認を求める。承認が得られるまでこのサイクルを繰り返す。

**❌ 絶対禁止の行為:**
- ユーザーの承認を得ずにステップ5(実装)を開始すること。
- 承認を求めずに自己判断で「承認された」とみなして実装に進むこと。

## ステップ4.6: 作業ブランチの作成 (create-branch の実行)

**承認取得後、実装に着手する前に、この作業単位専用の作業ブランチを切る。**

1. `create-branch` コマンドを実行してブランチを切る:
  - `Skill('create-branch')` を実行し、引数として **作業単位に対応するブランチ名** を渡す。
  - ブランチ名は `feature/[作業単位名]` とする(ブランチ戦略のプレフィックス規約、および `commit-steering` の `feature/<名>` 命名に整合)。
  - 親ブランチは `create-branch` がブランチ戦略に基づき `dev` を選択する。`dev` が未整備の場合は `create-branch` の指示に従い、ユーザー確認を得てから進める。
2. ステップ1/4で作成した3つのステアリングファイル(`requirements.md` / `design.md` / `tasklist.md`)は未コミットの変更として新ブランチに引き継がれる。これを確認する。
3. 現在のブランチが `feature/[作業単位名]` になっていることを確認したうえで、ステップ5に進む。

**このステップが正常に完了したら、決して停止せず、ただちにステップ5に進むこと。**

## ステップ5: 実装ループ (tasklist.mdの完全消化)

**このステップは、`tasklist.md`の全タスクが `[x]` になるまで自動で繰り返されるループ処理です。**
**このステップが正常に完了したら、決して停止せず、ただちにステップ6に進むこと。**

**ループ開始:**

1. タスクリストの読み込み:
  - `[ステアリングディレクトリパス]/tasklist.md`ファイルを読み込む。

2. 進捗の確認:
  - ファイル内に未完了タスク (`[ ]`) が存在するか確認する。
  - **もし未完了タスクが存在しない場合:** この実装ループは完了とみなし、ただちに**ステップ6**へ進む。
  - **もし未完了タスクが存在する場合:** 次の処理（3. タスクの実行）に進む。

3. タスクの実行:
  - `tasklist.md`の**先頭にある未完了タスク**を1つ特定する。
  - そのタスクを完了させるために必要な実装作業を実行する。
  - `Skill('steering')`を**実装モード**で使用する。
  - `Skill('development-guidelines')`のコーディング規約（特にレイヤー依存 UI→サービス→データ）を常に遵守する。

4. タスクリストの更新:
  - 実行したタスクが完了したら、`Edit`ツールを使用して`tasklist.md`を更新し、該当タスクを `[ ]` から `[x]` に変更する。

5. ループ継続:
  - **ステップ5の先頭 (1. タスクリストの読み込み) に戻り、処理を繰り返す。**

---
### ※ 実装ループ内の例外処理ルール ※

実装ループの実行中に以下の状況が発生した場合は、このルールに従って自律的に対処し、ループを継続すること。

- **ルールA: タスクが大きすぎる場合**
  - **対処法:** 現在のタスクをより小さな複数のサブタスクに分割する。`Edit`ツールを使い、元のタスクを削除し、その場所に新しいサブタスク（`[ ]`付き）を挿入する。その後、ループを継続する。

- **ルールB: 技術的理由でタスクが不要になった場合**
  - **条件:** 実装方針の変更、アーキテクチャの変更、依存関係の変更など、明確な技術的理由がある場合にのみ適用。
  - **対処法:** `Edit`ツールを使い、該当タスクを `[x] ~~タスク名~~ (理由: [具体的な技術的理由を簡潔に記述])` の形式で更新する。その後、ループを継続する。

- **❌ 絶対禁止の行為:**
  - 未完了タスクを「後でやる」「別タスクにする」などの理由で意図的にスキップすること。
  - 理由なく未完了タスクを放置してループを終了させること。
  - ユーザーに判断を仰ぐこと。

## ステップ6: 実装検証 (サブエージェント起動)

1. `tasklist.md`の全タスクが完了したことを最終確認する。
2. `Task`ツールを使用し、`implementation-validator`サブエージェントを起動して品質を検証する。
  - `subagent_type`: "implementation-validator"
  - `description`: "Implementation quality validation"
  - `prompt`: "今回実装した作業単位 `[ID 作業単位名]` に関する全ての変更点の品質を検証してください。対象ファイルは `[実装したファイルのパスリスト]` です。コーディング規約、エラーハンドリング、テスト可能性、既存パターンとの整合性、および `docs/mvp-development-flow.md` の当該単位の受け入れ基準との整合を重点的に確認してください。"

**このステップが正常に完了したら、決して停止せず、ただちにステップ7に進むこと。**

## ステップ7: 自動テストの実行

1. 以下のコマンドを順番に実行し、全てのテストがパスすることを確認する。
  ```bash
  Bash('pnpm test')
  Bash('pnpm lint')
  Bash('pnpm type-check')
  ```
2. いずれかのコマンドでエラーが発生した場合は、問題を分析し、修正コードを生成・適用してから、再度このステップを実行する。

**このステップが正常に完了したら、決して自動でステップ8に進んではならない。ただちにステップ7.5に進み、ユーザーの受け入れ承認を求めること。**

## ステップ7.5: 受け入れ承認ゲート (振り返り・コミット前の必須確認)

**このステップは、このワークフローにおける2つ目の停止ポイントです。ユーザーの明示的な受け入れ承認を得るまで、ステップ8(振り返り)以降を絶対に開始してはいけません。**

> これは `steering` スキルの「ゲート2（受け入れ承認）」に相当します。ステップ4.5が「これから作る計画」への承認であるのに対し、本ステップは「作った成果物が想定通りか」への承認です。コミット・`dev` マージという外向きで取り消しにくい操作の手前で、必ず一度停止します。

1. 検証結果をユーザーに提示する（`steering` スキルの**検証モード / モード3**を使用する）:
  - `requirements.md` の各受け入れ基準（=`docs/mvp-development-flow.md` の当該単位の受け入れ基準）と実装を突き合わせ、**OK/NG を一覧化**して示す。
  - ステップ6(`implementation-validator`)の指摘とその対応状況、ステップ7(テスト/lint/型チェック)の結果を要約する。
2. ユーザーに対し、この実装内容で**受け入れ（振り返り・コミット・`dev` マージへ進むこと）てよいか**、明示的に承認を求める。**あわせて、次フェーズ（受け入れ・振り返り・コミット）の推奨モデルと切り替え方法を案内する。**
  - 例: 「上記の検証結果です。この内容で受け入れ、振り返り・コミット・`dev` へのマージまで進めてよろしいですか？ NG や修正が必要な点があればご指示ください。\n承認後は振り返り・ドキュメント更新・コミットに入ります。判断とドキュメント更新を伴うため **Opus** を推奨します。承認前に `/model opus` への切り替えをおすすめします（切り替えなくても続行可能です）。」
3. **ユーザーの応答を待つ。ここで必ず処理を停止すること。**
  - **承認された場合** (例: 「OK」「承認」「進めて」など肯定的な応答): ステップ8(振り返り)に進む。ユーザーがこの停止中に `/model opus` へ切り替えていれば、以降は Opus で実行される。
  - **NG・修正を求められた場合:** `steering` スキルの「検証 → 戻る」に従い、不一致の原因を分類(A: 実装欠陥 / B: 設計の前提崩れ / C: 要件の認識ズレ)してユーザー確認を取り、対応する戻り先へ戻る。**戻り先フェーズに応じて推奨モデルへの切り替えをあわせて案内する。**
    - **分類A（実装欠陥）:** `tasklist.md` に修正タスクを追加してステップ5(実装ループ)へ戻り、再実装後ステップ6→7→7.5を再実行する（計画の再承認=ステップ4.5は不要）。実装フェーズに戻るため **Sonnet**（`/model sonnet`）を推奨する。
    - **分類B/C（設計/要件の前提崩れ）:** `design.md` / `requirements.md` を見直し、`tasklist.md` を再計画したうえで**ステップ4.5(計画承認)から**やり直す。計画フェーズに戻るため **Opus**（`/model opus`）を推奨する。設計・要件の変更が MVP の前提に及ぶ場合は、`docs/` 側の永続ドキュメントと `docs/mvp-development-flow.md` の該当記述の是正もあわせて検討する。
  - 各ラウンドは `tasklist.md` の「検証ログ」に記録する。

**❌ 絶対禁止の行為:**
- ユーザーの受け入れ承認を得ずにステップ8(振り返り)・ステップ9(コミット/マージ)を開始すること。
- NG項目が残ったまま「全タスク `[x]` だから完了」とみなして先へ進むこと。
- 承認を求めずに自己判断で「承認された」とみなすこと。

## ステップ8: 振り返りとドキュメント更新

1. `Skill('steering')`を**振り返りモード**で実行し、`tasklist.md`に申し送り事項を記載する。
  - 実装完了日
  - 計画と実績の差分
  - 学んだこと
  - 次回への改善提案

2. 今回の変更がプロジェクトの基本設計やアーキテクチャに影響を与えるか判断する。

3. 影響がある場合、`docs/`内の関連する永続ドキュメントを`Edit`ツールで更新する。

4. **`docs/mvp-development-flow.md` の進捗を更新する（本コマンド必須の工程）:**
  - 「進捗」表の当該作業単位の行を `Edit` ツールで更新する:
    - **状態**を `✅ 完了 (YYYY-MM-DD)`（実装完了日）に変更する。
    - **steering ディレクトリ**列を今回のパス（`.steering/[日付]-[作業単位名]/`）に更新する。
  - 当該単位の完了により「MVP完成の定義（Definition of Done）」の該当チェックボックス（`- [ ] U…`）が満たされた場合は、`- [x]` に更新する。
  - 実装過程で判明した設計・スコープの変更を「作業単位一覧」や依存グラフに反映すべき場合は、あわせて `docs/mvp-development-flow.md` を是正する（永続ドキュメント側を正とし、本書はそれに追従する）。

**このステップが正常に完了したら、決して停止せず、ただちにステップ9に進むこと。**

## ステップ9: コミット & dev へのマージ

**作業ブランチ(`feature/[作業単位名]`)上の全変更をコミットし、`dev` へマージする。**

1. コミット対象の確認とステージング:
  - `git status` で変更内容を確認する。
  - ステアリングファイル、実装コード、更新した `docs/`（`docs/mvp-development-flow.md` の進捗更新を含む）等、今回の作業に関する全変更をステージングする(`git add`)。

2. コミット:
  - `Skill('development-guidelines')` のコミットメッセージ規約に従い、意味のある単位でコミットする。
  - 作業単位の内容を表す簡潔なコミットメッセージを付ける（例: `feat(...): [作業単位名] を実装 ([ID])`）。

3. `dev` へのマージ:
  - `dev` を最新化する:
    ```bash
    git fetch origin --prune
    ```
  - `dev` が存在しない場合は、ステップ4.6(`create-branch`)で合意した方針に従う(`main` から `dev` を作成する等)。
  - `dev` に切り替えて作業ブランチをマージする:
    ```bash
    git switch dev
    git merge --no-ff feature/[作業単位名]
    ```
  - マージコンフリクトが発生した場合は解決し、テスト(`pnpm test` / `pnpm lint` / `pnpm type-check`)が通ることを再確認してからマージを確定する。

4. リモートへの反映:
  - `git push origin dev` で `dev` を更新する。
  - push 後、`dev` の HEAD が今回のマージコミットになっていることを確認する。

5. 結果報告:
  - 対象作業単位、作成したブランチ、コミット、マージ先(`dev`)、push 結果、および `docs/mvp-development-flow.md` の進捗更新結果を報告する。
  - あわせて「進捗」表に基づく**次の作業単位**を案内する。

> 補足: `docs/development-guidelines.md` のブランチ戦略は本来 PR 経由でのマージを推奨しているが、本ワークフローはユーザー指示により `dev` への直接マージまでを自動実行する。

## 完了条件

このワークフローは、以下の全ての条件を満たした時点で自動的に完了となる。
- ステップ1: `docs/mvp-development-flow.md` の進捗表に基づき、依存が解決済みの対象作業単位が特定されている。
- ステップ4.6: `feature/[作業単位名]` の作業ブランチが作成され、チェックアウトされている。
- ステップ5: `tasklist.md`の全てのタスクが完了状態（`[x]`または正当な理由でスキップ）になっている。
- ステップ6: `implementation-validator`サブエージェントの検証をパスする。
- ステップ7: `test`, `lint`, `type-check`の全てのコマンドがエラーなく成功する。
- ステップ7.5: 検証結果(受け入れ基準のOK/NG)を提示し、ユーザーの受け入れ承認を取得している。
- ステップ8: `tasklist.md`に申し送り事項が記載され、かつ **`docs/mvp-development-flow.md` の「進捗」表が当該作業単位について更新されている**。
- ステップ9: 全変更がコミットされ、`dev` へマージ・push されている。

この完了条件を満たすまで、自律的に思考し、問題解決を行い、作業を継続すること。
