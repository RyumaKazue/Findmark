# steering単位のコミット & プッシュ

引数で渡された情報から `.steering/` 配下の対象ディレクトリを特定し（**引数省略時は最新の steering を対象**）、
**ユーザーの承認を得てから**、その steering に対応する変更を
**steering 専用ブランチ（`feature/<機能名>`）上で**
ステージング → コミット → プッシュまで実行します。
現在のブランチが対象ブランチでない場合は、`dev` をベースに専用ブランチを切ってからコミットします。

引数: **任意**。steering を特定できる情報（ディレクトリ名の一部・機能名・日付など）。
**省略した場合は、最終更新が最も新しい steering を自動対象にします。**

## 実行方法

```bash
claude
> /commit-steering                          # 引数なし → 最新の steering を対象
> /commit-steering sw-navigation
> /commit-steering レベルC ナビゲーション
> /commit-steering 20260618-sw-navigation-levelc
```

## 手順

### ステップ1: steering の特定

`.steering/` 配下のディレクトリ一覧を取得する（`ls .steering/`）。
`.steering/` が空（0件）なら、その旨を提示して終了する。

**引数の有無で分岐する:**

#### 1-A. 引数がない場合（最新の steering を自動対象）

- `.steering/*/` 配下ファイルの**最終更新時刻（mtime）が最も新しい**ディレクトリを対象にする。
  - 判定方法: `ls -t .steering/*/* 2>/dev/null | head -1` で最新更新ファイルを取得し、その**親ディレクトリ**を対象 steering とする。
  - （ディレクトリ mtime ではなく配下ファイルの mtime を見る。ファイル内容の編集を確実に反映するため）
- 自動選択した steering は**必ずステップ3の承認で「最新として自動選択した」旨を明示**し、ユーザーに確認させる。
- 特定できたらステップ2へ。

#### 1-B. 引数がある場合

1. 引数の文字列を手がかりに、一致する steering ディレクトリを探す。
   - ディレクトリ名（`[YYYYMMDD]-[機能名]`）に対する部分一致を最優先する。
   - ディレクトリ名で一意に決まらない場合は、各 steering の
     `requirements.md` の `## 概要` を読み、内容との一致で絞り込む。
2. 結果に応じて分岐する:
   - **1件に特定できた** → ステップ2へ。
   - **複数候補がある** → 候補を一覧で提示し、`AskUserQuestion` で
     ユーザーにどれか選んでもらう。選択後ステップ2へ。
   - **0件** → 候補が見つからない旨と `.steering/` の一覧を提示し、終了する。
     （勝手に推測してコミットしない）

### ステップ2: 対象ファイル・コミットメッセージ・ブランチの算出

以下を**自動で**組み立てる（ファイル選択・メッセージともユーザーに確認しない）:

1. **対象ファイルの自動算出**
   - 特定した steering の `requirements.md` / `design.md` / `tasklist.md` を読み、
     本文中で言及されている実装ファイルのパスを抽出する。
   - `git status --porcelain` で変更中のファイル一覧を取得する。
   - 「steering が言及するパス」∩「実際に変更されているファイル」を
     ステージング対象として確定する。
   - 加えて、その steering 自身のディレクトリ
     （`.steering/[特定したディレクトリ]/` 配下、主に `tasklist.md`）の
     変更もステージング対象に含める。
   - **注意**: `.steering/` には複数の作業が並行して存在しうる。
     `git add -A` や `git add .` は使わず、必ず算出した対象ファイルのみを対象にする。
2. **コミットメッセージの自動生成**
   - `requirements.md` の `## 概要` と `design.md` の内容を理解し、
     その steering で何を実装したかを表す簡潔な日本語1行メッセージを生成する。
   - リポジトリ既存の慣習（体言止め「〜の実装」等。例:「バックグラウンド処理の実装」）に合わせる。
   - **このメッセージはユーザーに確認しない。** 自分で適切に決定する。
3. **対象ブランチの算出**
   - `機能名` = 対象 steering ディレクトリ名から先頭の `YYYYMMDD-` を除いた文字列
     （例: `20260724-manifest-permissions` → `manifest-permissions`）。
   - `targetBranch` = `feature/<機能名>`（例: `feature/manifest-permissions`）。
   - `currentBranch` = `git rev-parse --abbrev-ref HEAD` で取得する。
   - これらも自動確定し、ステップ3の承認材料として提示する（ユーザーには確認せず自分で決める）。

### ステップ3: steering 承認（必須ゲート）

`AskUserQuestion` で、**特定した steering で合っているか**だけを確認する。
提示する内容:

- 特定した steering ディレクトリ名
  - **引数なしで自動選択した場合は「最新として自動選択した」旨を明示する**
- 参考として、ステージ予定ファイル一覧
- **ブランチ操作の予告**:
  - `currentBranch == targetBranch` の場合: 「既に `targetBranch` 上のため、そのままコミットする」
  - 異なる場合: 「`currentBranch` → `targetBranch` に切替（無ければ `dev` をベースに作成）してからコミットする」
- 「この steering で commit & push を進めてよいか？」を Yes/No で問う

**この承認を得るまで、いかなる git 書き込み操作（`git fetch` は可、`git branch` / `git checkout -b` / `git add` / `git commit` / `git push`）も実行してはならない。**
承認するのは steering の特定（と、それに伴うブランチ操作）が正しいかどうかのみ。
ファイル選択とコミットメッセージは自動確定済みであり、改めて確認しない。
（特定が誤っている場合はユーザーが別の steering を指定し直す）

### ステップ4: ブランチ切替 → ステージング → コミット → プッシュ

steering の承認後、次の順で実行する。

#### 4-1. ブランチ判定

- `currentBranch == targetBranch` の場合 → **既に steering 専用ブランチ上**。ブランチ操作はせず「4-4. ステージング」へ直行する。
- 異なる場合 → 4-2, 4-3 を実行してから 4-4 へ。

#### 4-2. ベース `dev` の解決（`currentBranch != targetBranch` のときのみ）

1. `git fetch origin` を試行する（オフライン等で失敗しても致命ではない。ローカル参照で継続）。
2. 次の優先順で `dev` を用意する:
   - **`origin/dev` がある** → ローカル `dev` が無ければ用意する（`git checkout -b dev origin/dev` 相当。ただし後続の feature 作成で `dev` を start-point に使えればよい）。
   - **ローカル `dev` のみある** → それを使う。
   - **`dev` がどこにも無い** → `origin/main`（無ければローカル `main`）から `dev` を作成する（`git branch dev origin/main`）。
     **`dev` を新規作成した事実は、ステップ5の報告に必ず含める。**

#### 4-3. feature ブランチの用意（未コミット変更を保持したまま）

`targetBranch` の存在に応じて分岐する（いずれも作業ツリーの未コミット変更は保持される）:

- **ローカルに `targetBranch` が既存** → `git checkout <targetBranch>`。
- **`origin/<targetBranch>` が既存** → それを追跡して checkout する。
- **どちらも無い** → `git checkout -b <targetBranch> dev`（`dev` をベースに作成）。

`git checkout` が作業ツリーの競合で失敗した場合は、**出力をそのまま提示して停止する**（`--force` / `stash` 等で勝手に回避しない）。

#### 4-4. ステージング → コミット → プッシュ

算出した対象ファイルのみを対象に実行する:

```bash
git add <算出したファイル ...>          # -A / . は使わない
git commit -m "<自動生成したメッセージ>"
git push -u origin <targetBranch>       # 新規/未追跡ブランチのため -u を付ける
```

- upstream が既に設定済みなら `git push` でよい。
- いずれかのコマンドが失敗したら、出力をそのまま提示して停止する
  （勝手に `--force` 等で回避しない）。

### ステップ5: 結果報告

```markdown
✅ steering「[ディレクトリ名]」を feature/[機能名] にコミット & プッシュしました

- ブランチ: [targetBranch]（[新規作成 / 既存へ切替 / 既にこのブランチ上]、ベース: dev[（dev も新規作成）]）
- コミット: [短縮ハッシュ] [メッセージ]
- ステージしたファイル: N件
- push 先: origin/[targetBranch]
```

- 引数なしで自動選択した場合は、対象 steering を「最新として自動選択した」旨も併記する。

## 注意事項

- ステアリングの特定ミスは手戻りが大きいため、**steering の承認なしに git 書き込み操作を行わない**こと（承認前に許されるのは読み取りと `git fetch` まで）。
- 確認するのは「steering の特定（と、それに伴うブランチ操作）が正しいか」のみ。ファイル選択・コミットメッセージ・ブランチ名は
  自動で確定し、ユーザーには確認しない。
- **コミットは常に steering 専用ブランチ `feature/<機能名>` 上で行う**。`main` や無関係なブランチへ直接コミット・push しない。
- `dev` を新規作成した場合は、その副作用を隠さずステップ5で明示する。
- ステージングは steering に関連するファイルのみに限定し、
  並行作業中の他 steering の変更を巻き込まない（`git add -A` / `git add .` は使わない）。
- コミットメッセージは steering の内容を理解した上で、
  リポジトリ既存の簡潔な日本語スタイル（体言止め「〜の実装」等）に合わせて自分で決める。
- ブランチ切替・push が失敗したら、勝手に `--force` / `stash` 等で回避せず、出力を提示して停止する。
