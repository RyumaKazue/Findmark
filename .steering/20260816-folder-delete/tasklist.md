### 学んだこと

**技術的な学び**:
- **既存モードへの相乗りは、モードが提供する「キー意味論の集合」が必要十分なときに限って正しい**。`PANEL` は「全ショートカット抑止 + ↑↓/Enter/Escape」を既に持っており、メニューにも確認ダイアログにもそのまま合った。新しい `Mode` を足していたら同じ意味論を2度定義することになった。一方で PANEL 用途が4つに増え、排他条件の管理コストが実際に問題化し始めている（design.md に `panelKind` ユニオンへの統合を申し送り済み）。**「相乗りは正しいが、相乗り先の管理方法は別途見直す時期に来ている」**という二段構えの結論になった。
- **破壊的操作は「順序」が設計そのもの**。`getSubTree` → 退避データ組み立て → `removeTree` の順は入れ替え不可能（削除後は部分木が読めない）。この種の「やり直しの効かない順序」はコードコメントに理由を書いておかないと、後のリファクタで平気で入れ替えられる。
- **オーバーレイで塞ぐ設計は「塞ぎ漏れ」を生む**。既定メニューの抑止をオーバーレイに閉じ込めると、オーバーレイの外（ペインの空白・2回目の右クリック）が漏れる。「どこをクリックしても同じ結果」を保証したいなら、面ではなく**ドキュメント全体のルール**として書くほうが穴が塞がる。ただし全面禁止は入力欄の利便性を壊すため、例外（`input`/`textarea`/`contenteditable`）を明示的に持たせた。
- **メニューの初期フォーカスは「無し」が既定**。先頭を初期選択にすると、開いた直後の `Enter` が最上位項目を実行する。破壊的項目が並ぶメニューでは、これは確認ダイアログの既定フォーカスを[キャンセル]にした配慮を台無しにする。同じ「誤発火を防ぐ」観点が UI の2箇所で必要だった。
- 外部 API の例外仕様（`normalizer.hashUrl` が不正 URL で throw する）は、**既に同じ問題を解いている既存コード**（`SearchEngine.lookupAliases` の try/catch）が教えてくれた。新しい呼び出し口を作るときは、同じ関数の既存呼び出し箇所がどう守っているかを先に見るべきだった。

**プロセス上の改善点**:
- 実装前に「フォルダ削除機能は本当に無いのか」を、UI・フック・データ層・PRD の4方向から確認したことで、**受け皿（TrashStore の `kind:'folder'`）が既に完成している**という重要な前提を掴めた。おかげで新規実装は「削除する側」だけに絞れた。
- 一方、**マウス操作の細部（右クリックの2回目・ハイライトの見え方）は自動テストでも検証エージェントでも捕まらなかった**。ユーザーの実機確認が2ラウンドとも発見源だった。UI の触感を含む単位では、受け入れ前に手動確認の観点を明示的に提示すべきだった。

### 次回への改善提案
- **右クリック/長押し/ドラッグのような「ブラウザ既定の挙動と競合する操作」を実装するときは、要件段階で「既定挙動をどう扱うか」を必ず1項目立てる**。今回は AC-1 に「既定メニューではなく独自メニューを開く」とは書いたが、「メニュー表示中の2回目」までは想定しておらず、そこが抜けた。
- 受け入れ提示の際に、**自動テストで担保できない確認観点をチェックリストとして渡す**（今回は「2回目の右クリック」「入力欄でのコピー/貼り付け」「メニューのハイライト」が該当）。ラウンドを減らせる。
- PANEL 用途が5つ目に増える前に、`panelKind` ユニオンへの統合リファクタを独立した単位として実施する（本単位の design.md に申し送り済み）。排他条件の追加漏れは静かに壊れる種類のバグで、テストでも気づきにくい。
